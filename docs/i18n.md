# Languages, text direction, and regional sites

This document describes how the server supports several languages, how it chooses the language of each request, and how frontends lay out right-to-left (RTL) and left-to-right (LTR) languages. It is the work of [#283](https://github.com/mdastpak/Crypto-Exchange/issues/283) (locales and translations); [#284](https://github.com/mdastpak/Crypto-Exchange/issues/284) (GeoIP, [geoip.md](geoip.md)), [#285](https://github.com/mdastpak/Crypto-Exchange/issues/285) (a domain and locales per country), and [#286](https://github.com/mdastpak/Crypto-Exchange/issues/286) (the user's saved language and theme) build on it.

## Locales

`i18n.locales` lists the supported locales as BCP 47 tags, such as `fa` or `en-GB`, and `i18n.default_locale` the fallback ([configuration](configuration.md#i18n)). The default is `[en, fa]` with `en` as the fallback. English is always supported, because `en.json` defines every message, and so it is the language of every message that has no translation.

The server derives the rest of each locale from its language, so that the configuration cannot contradict it:

| Field | From | Example for `fa` |
| --- | --- | --- |
| `name` | the English name of the language (CLDR) | `Persian` |
| `native_name` | the name of the language in itself, for a language switcher | `فارسی` |
| `dir` | the script the language is written in: Arabic, Hebrew, Thaana, Syriac, N'Ko, Adlam, Hanifi Rohingya, Mandaic, Samaritan, and Mende Kikakui are `rtl`, every other is `ltr` | `rtl` |

So `fa`, `ar`, `he`, `ur`, `ps`, and `ckb` are RTL; `az` is LTR, but `az-Arab` is RTL. `GET /api/v1/public/locales` ([API](api.md#get-publiclocales)) returns the list.

## The locale of a request

`internal/i18n.Middleware` chooses the locale of every request, before the rate limits, so that every answer, refusals included, can use it. It takes the first of these that names a supported locale:

1. The `lang` query parameter: a choice for this request, such as a link to a page in another language.
2. The `X-Locale` header: the choice of an app, which has no cookies. CORS allows it.
3. The `locale` cookie: the choice that the visitor made in the language switcher, which the frontend saves.
4. The browser's `Accept-Language`, matched closely: `fa-IR` finds `fa`, and `en-GB` finds `en`, but Turkish does not find Azerbaijani.
5. `i18n.default_locale`.

A value that names no supported locale is skipped, never an error, so that a stale cookie or a link in a language that a release does not offer still gets an answer. A tag finds the locale of its language when its own region is not listed: `fa-AF` finds `fa`.

The first three are the visitor's explicit choice. Later steps, such as the site of a country in #285, must never override an explicit choice; `i18n.Negotiated.Explicit` reports it.

## Messages

Handlers never write the text of a message: they send a message key and the values of its parameters, `i18n.M("NOT_FOUND")`, and the response envelope renders it in the locale of the request ([#290](https://github.com/mdastpak/Crypto-Exchange/issues/290)). Every language has one catalog in `internal/i18n/catalogs`, named by its tag and embedded in the binary: `en.json`, the source of every key, and the translations, such as `fa.json`. A catalog is a flat map of keys, in upper case with underscores, to texts:

```json
{
  "NOT_FOUND": "Not found",
  "CURRENCY_OPERATION_UNAVAILABLE": "The {operation} of {currency} is not available now.",
  "CAPABILITY_BUY": "buying"
}
```

```json
{
  "NOT_FOUND": "یافت نشد.",
  "CURRENCY_OPERATION_UNAVAILABLE": "{operation} ارز {currency} در حال حاضر در دسترس نیست.",
  "CAPABILITY_BUY": "خرید"
}
```

### Parameters

A text names its parameters in braces, `{currency}`, in lower case, and each language puts them where its grammar needs them; `{{` and `}}` write a literal brace. The value of a parameter is one of:

- **A key or a message**, which is rendered in the same locale, so that a part that changes with the state of the system is translated too: `i18n.A("operation", i18n.Key("CAPABILITY_BUY"))` reads `buying` in English and «خرید» in Persian. A message can nest another message with parameters of its own.
- **A literal**, such as a currency symbol, an amount, or a date, which is inserted as it is. In an RTL locale it is wrapped in Unicode isolates (U+2068 and U+2069), so that `BTC/USDT`, an address, or a number keeps its own direction inside Persian text.

```go
helpers.SendError(c, http.StatusForbidden, CodeCurrencyOperationDisabled,
    i18n.M("CURRENCY_OPERATION_UNAVAILABLE",
        i18n.A("operation", i18n.Key("CAPABILITY_"+strings.ToUpper(string(capability)))),
        i18n.A("currency", symbol)),
    info)
```

renders as `The buying of BTC is not available now.` in English and «خرید ارز BTC در حال حاضر در دسترس نیست.» in Persian. A key built from a value, as here, is one of a family (`CAPABILITY_*`, `CHANNEL_*`, `FAVORITE_KIND_*`): every value of the family needs its key, and the tests of the package that builds it check that.

### Rendering

`helpers.SendResponse` and `helpers.SendError` render the message of every answer, of any status, from the catalog of the locale, or of its language (`fa-AF` uses `fa.json`), and else from `en.json`. A key that no catalog has renders as the key itself, never as an empty text, and a parameter without a value renders as nothing. `Message.String()` renders a message in English, for logs. The `code` of an error never changes, so a client that acts on codes is not affected by the language.

Every answer of the envelope says the language its message is in, in `Content-Language`. Error answers and translated answers carry `Vary: Accept-Language, Cookie, X-Locale`, so that a cache never shows one visitor's language to another.

Field-level validation texts in `info.errors` stay in English: clients show their own texts for them, by field and code. The messages of the WebSocket stream are not translated yet.

### Adding a language

1. Add its tag to `i18n.locales`. Its names and direction come from the language.
2. Optionally, add `internal/i18n/catalogs/<tag>.json` with the translations. Without it, the locale is offered and the API's messages stay in English; a key that it lacks falls back to English.
3. `go test ./internal/i18n` checks every catalog: it parses, defines only keys of `en.json`, and each translation has the same parameters as the English text.

### Adding or changing a message

Add the key to `en.json` and to `fa.json`, which must translate every key, and send it with `i18n.M`. The test above fails when a handler sends a key that `en.json` lacks, and when `en.json` has a key that no Go file sends any more, so that a removed message does not leave a stale entry behind. Change the text of a key to reword a message; give it a new key when its meaning changes, so that no translation keeps the old meaning.

## Right-to-left and left-to-right layout

The server tells frontends the direction of each locale; the layout is the frontend's work. The rules:

- **Root element.** Set `lang` and `dir` on `<html>` from `current` of `GET /public/locales` (or from the locale the visitor picked): `<html lang="fa" dir="rtl">`. Never derive the direction from the text.
- **Logical CSS.** Use logical properties and values, which follow the direction: `margin-inline-start` instead of `margin-left`, `padding-inline-end`, `inset-inline-start`, `text-align: start`, `border-start-start-radius`. Flex and grid follow `dir` by themselves. Mirror directional icons (arrows, chevrons, "back"), but not icons of things, such as a clock, a play button, or a chart.
- **Forms.** Labels, inputs, help texts, and error messages follow the page direction. Fields whose content is always LTR keep `dir="ltr"` inside an RTL form, aligned to the start of the page: email addresses, mobile numbers, wallet addresses, transaction hashes, amounts with their symbols, and codes. Sign-in already accepts Persian and Arabic digits and normalises them ([#197](https://github.com/mdastpak/Crypto-Exchange/issues/197)).
- **Mixed content.** Wrap LTR runs inside RTL text, and text of unknown direction such as user names, in `<bdi>` or `dir="auto"`, so that symbols such as `BTC/USDT` and numbers keep their order. Names cannot contain bidi override characters: the profile rejects them.
- **Numbers and dates.** Format them with `Intl.NumberFormat` and `Intl.DateTimeFormat` for the locale; the API always sends numbers with ASCII digits and instants in RFC 3339 UTC. Show prices and amounts in a stable direction (`dir="ltr"`) in tables so that columns line up.
- **Charts and order books.** Keep time axes and price ladders in their usual direction in every locale; mirror only the chrome around them.

## Multi-node deployments

The catalogs are embedded in the binary, and the locales come from the configuration, so every instance answers the same with no shared state. During a rolling deploy two versions may answer with different catalogs; only message texts can differ, never codes.
