# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). No versions have been tagged yet, so entries are grouped by the date the changes reached `main`. Semantic versioning will start with the first tagged release.

## [Unreleased]

### Added

- Project documentation: `README.md`, `SECURITY.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `docs/architecture.md`, `docs/configuration.md`, and `docs/api.md`.
- Issue templates and a pull request template.
- Test-scenario catalog with stable scenario IDs and a finding-status table, in [`docs/testing/test-scenarios.md`](docs/testing/test-scenarios.md) ([#90](https://github.com/mdastpak/Crypto-Exchange/pull/90)).
- Sign-in codes are delivered by email (SMTP) and by SMS (Kavenegar verify lookup). Codes are queued on the `notifications` exchange and delivered by a worker that retries temporary failures with exponential backoff until `notifications.worker.max_attempts` or the code expiry, and records codes it cannot deliver on the `notifications.otp.dead-letter` queue without the code or the raw contact. Channels are configured in the new `notifications` section, with the `SMTP_PASSWORD` and `KAVENEGAR_API_KEY` environment variables for secrets ([#14](https://github.com/mdastpak/Crypto-Exchange/issues/14)).
- Separate signing keys for admin tokens (`jwt.ssl.admin`), which were configured but never loaded, and `retired_public_keys` for each role, so that signing keys can be rotated without signing everyone out. Tokens name their key in the `kid` header ([#17](https://github.com/mdastpak/Crypto-Exchange/issues/17)).
- Admin sign-in with two factors: a one-time code sent by email, and a code from an authenticator app (TOTP). Operators create administrators with the new `cmd/admin` command (`create`, `reset-totp`, `disable`), which prints the authenticator enrollment once. Authenticator secrets are encrypted with the new `admin.totp_key` (`ADMIN_TOTP_KEY`), and each authenticator code is accepted once. Migration 12 adds `users.role` and `users.totp_last_step`. New routes: `POST /admin/auth`, `POST /admin/auth/{uuid}`, and `POST /admin/logout` ([#18](https://github.com/mdastpak/Crypto-Exchange/issues/18)).
- Every setting that `.env.example` lists can be set with its environment variable, and `docs/configuration.md` lists every variable the server reads. A test checks that each variable in `.env.example` is read. The `app` service of `docker-compose.yml` receives `.env` when it exists, so copying `.env.example` to `.env` and running `docker compose up` starts a working server ([#29](https://github.com/mdastpak/Crypto-Exchange/issues/29)).
- `PATCH /user/profile` changes the first, last, and display names of the signed-in user, with validation. Only the fields sent change, and every other field is rejected ([#27](https://github.com/mdastpak/Crypto-Exchange/issues/27)).
- A CI workflow builds the Docker image on every pull request and checks that the Dockerfile uses the Go version of `go.mod`, that the image holds only the binaries and the migrations, and that it runs as a non-root user ([#28](https://github.com/mdastpak/Crypto-Exchange/issues/28)).
- A CI workflow checks every pull request and every push to `main`: build, `go vet`, `gofmt`, `go mod tidy -diff`, the whole test suite with the race detector against PostgreSQL, Redis, and RabbitMQ, `govulncheck`, and markdownlint. The test job fails when a test skips itself because a service is unreachable, and it keeps the coverage profile and the test log as an artifact. Dependabot proposes weekly updates of Go modules, GitHub Actions, and Docker base images ([#36](https://github.com/mdastpak/Crypto-Exchange/issues/36)).
- `golangci-lint` v2 runs in CI. `.golangci.yml` is migrated to the v2 format, which the keys of the old file did not fit. It enables `errcheck`, `gosec`, `govet`, `ineffassign`, `nolintlint`, `revive`, `staticcheck`, `unused`, and the `goimports` formatter, with a few narrow exclusions, each explained in the file. Every `//nolint` must name its linter and give a reason ([#40](https://github.com/mdastpak/Crypto-Exchange/issues/40)).
- Data-protection keys for the row seals and field encryption to come ([#139](https://github.com/mdastpak/Crypto-Exchange/issues/139), [#140](https://github.com/mdastpak/Crypto-Exchange/issues/140)). Keys of three purposes (`row-mac`, `field-enc`, `blind-index`) are generated by the server and stored in the new `data_keys` table (migration 15), wrapped by a key-encryption key that stays in the Transit engine of HashiCorp Vault or OpenBao. For development, a local key-encryption key can be used instead; release mode refuses it. The new `keys` settings select the provider. With one set, the server unwraps the keys at startup, creates the first version of each on the first start, and refuses to start when a key cannot be unwrapped or was moved to another row. The new `admin keys` commands list, rotate, retire, and re-wrap the keys. [`docs/data-protection.md`](docs/data-protection.md) describes the key hierarchy and the runbook ([#138](https://github.com/mdastpak/Crypto-Exchange/issues/138)).

### Changed

- Moved the technical audit notes of 2026-09-14 from this file to [`docs/audits/2026-09-14-technical-audit.md`](docs/audits/2026-09-14-technical-audit.md).
- `config/config.local.yaml` is now ignored by Git.
- **Breaking:** HTTP CORS is configured with the new `server.cors.allowed_origins` setting. `websocket.allowed_origins` now only applies to WebSocket connections ([#12](https://github.com/mdastpak/Crypto-Exchange/issues/12)).
- **Breaking:** OTP verification no longer returns `refresh_token` in the response body. The refresh token is only delivered in the `refresh_token` cookie, which is now `SameSite=Strict` and scoped to `/public/auth`. Tokens issued before this change have no token type and are rejected, so users must sign in again ([#10](https://github.com/mdastpak/Crypto-Exchange/issues/10)).
- **Breaking:** OTP sign-in accepts only email addresses and mobile numbers. Usernames are rejected with `400`, and sign-in with a contact type whose channel is not configured is refused with `400` instead of reporting a code that is never sent. Existing accounts whose only contact is a username can no longer sign in ([#14](https://github.com/mdastpak/Crypto-Exchange/issues/14)).
- **Breaking:** release mode requires the new `otp.auth.secret` setting (or `OTP_SECRET`) of at least 32 bytes, and the server refuses to start with OTP settings out of range. `otp.auth.length`, `ttl_seconds`, and `retry_limit` now default to 6, 60, and 3. Sign-in codes issued before the upgrade can no longer be verified, so users must request a new one ([#15](https://github.com/mdastpak/Crypto-Exchange/issues/15)).
- **Breaking:** protected routes, including `POST /public/auth/logout`, now require `Authorization: Bearer <token>`. A bare token gets `401`. User routes accept only user tokens and admin routes only admin tokens, so admin tokens no longer reach `/user/*`, and a user token on an admin route gets `401` instead of `403`. Tokens issued before the upgrade have no `kid` and no audience and are rejected, so users must sign in again. `jwt.issuer` defaults to `encrypted-db-exchange` and is required on every token ([#17](https://github.com/mdastpak/Crypto-Exchange/issues/17)).
- **Breaking:** `GET /user/profile` returns the signed-in user's profile, with masked contacts, instead of the currency list. Clients that read currencies there must use `GET /public/currencies`. `POST /user/update`, which always returned `501`, is removed in favor of `PATCH /user/profile`. A token whose account was disabled, deleted, or suspended, or became an administrator account, after it was issued gets `403` from the profile routes ([#27](https://github.com/mdastpak/Crypto-Exchange/issues/27)).
- `server.mode` (or `SERVER_MODE`) now selects Gin's mode and the release checks, which only `GIN_MODE` did before. `GIN_MODE` still works, so a deployment that sets `GIN_MODE=release` keeps running in release mode, but a configuration file with `mode: "release"` now enables release mode, which requires `otp.auth.secret`. An unknown mode stops the server ([#29](https://github.com/mdastpak/Crypto-Exchange/issues/29)).
- The server stops at startup with one message that names every missing required setting and its environment variable, instead of failing later, for example with `Failed to initialize auth keys` for an empty key path. Invalid numbers or booleans in environment variables also stop it ([#29](https://github.com/mdastpak/Crypto-Exchange/issues/29)).
- JWT key paths are plain strings, such as `"internal/ssl/user/private_key.pem"`. Lists of path segments are still accepted ([#29](https://github.com/mdastpak/Crypto-Exchange/issues/29)).
- `config/config.yaml` is no longer tracked, as `.gitignore` already intended. If you edited it, copy it to `config/config.local.yaml` before you pull, because pulling removes an unchanged copy and stops on a changed one. `config/config.example.yaml` has no `${...}` placeholders anymore, which were never expanded and were used as literal passwords. It reads the user keys from `internal/ssl/user`, so it works as it is for a local run, and it is still the embedded fallback when no configuration file exists. `.env.example` uses `POSTGRES_DB`, the variable the server reads, instead of `POSTGRES_DBNAME` ([#29](https://github.com/mdastpak/Crypto-Exchange/issues/29)).
- Admin tokens are only issued to users whose stored role is `admin`, and every admin request checks that the administrator is still active, so demoting or disabling an administrator revokes its tokens at once. Administrators cannot use the user sign-in (`403`) ([#18](https://github.com/mdastpak/Crypto-Exchange/issues/18)).
- Updated Go modules: gin 1.12.0, golang-migrate 4.20.1, shopspring/decimal 1.6.0, validator 10.30.5, gin-swagger 1.6.1, and swag 1.16.6. pgx stays at 5.11.0 until 5.12.0 is two weeks old. Dependabot now proposes a release only once it is two weeks old (`cooldown`); security updates do not wait.
- The test suite no longer needs `go test -p 1`. Each package has a PostgreSQL database and a Redis database of its own; `internal/testutil/redistest` assigns the Redis databases. `go test ./...` runs the packages in parallel, in about a third of the time, and CI does the same ([#37](https://github.com/mdastpak/Crypto-Exchange/issues/37)).
- **Breaking:** one user model (migration 14). Contacts move from `users.info->'contact'` into the new `user_contacts` table, where the database enforces that each contact belongs to one user and records when it was verified. `users.status` becomes `account_status_type`: `approved` is now `ACTIVE`, `unverified` `PENDING_VERIFICATION`, `suspend` `SUSPENDED`, and `disabled` and `deleted` `INACTIVE`, with `deleted_at` as the only mark of deletion. `GET /user/profile` and `PATCH /user/profile` return the new status values. `users.info`, the never-written `email`, `phone`, and `*_verified` columns, and the unused `models.User` and `public.User` types are gone; `account.User` is the only Go type. The migration stops before any change, with a message that says what to fix, if `info` holds anything but contacts. The down migration restores the previous schema and data. An administrator's email address counts as verified after the first sign-in ([#38](https://github.com/mdastpak/Crypto-Exchange/issues/38)).
- **Breaking:** the project is renamed from Encrypted-DB to Crypto Exchange, after the repository. The Go module path is now `github.com/mdastpak/crypto-exchange`. The default `jwt.issuer` changes from `encrypted-db-exchange` to `crypto-exchange`, so a deployment that relies on the default signs everyone out once; set `jwt.issuer` (`JWT_ISSUER`) to the old value to keep issued tokens valid. The default tracing service name changes the same way. New authenticator enrollments show "Crypto Exchange", and enrollments made earlier keep working. Docker Compose uses the fixed project name `crypto-exchange`, with matching container and network names, so its volumes no longer depend on the name of the checkout folder. The example asset logos and the AML contact use `example.com` instead of a domain that the project does not own.
- The runtime stage of the Docker image is based on Alpine 3.24 instead of 3.22. Dependabot proposed the update and then closed its pull request as up to date, so it is applied by hand ([#132](https://github.com/mdastpak/Crypto-Exchange/pull/132)).
- Replaced unmaintained or superseded modules: `github.com/streadway/amqp`, which is archived, with `github.com/rabbitmq/amqp091-go` v1.16.0; `github.com/go-redis/redis/v8` with `github.com/redis/go-redis/v9` v9.23.0; and `gopkg.in/yaml.v2` with `go.yaml.in/yaml/v3` v3.0.6. Migrations run with the pgx driver of golang-migrate, so `github.com/lib/pq`, a second PostgreSQL driver, is no longer linked. The pgx driver keeps the `schema_migrations` table and its lock, so an existing database is not migrated again. go-redis v9 ignores context deadlines unless told otherwise, so the server's client turns `ContextTimeoutEnabled` on, as v8 behaved, and the rate limiters still give up on Redis at `rate_limits.timeout_ms` ([#39](https://github.com/mdastpak/Crypto-Exchange/issues/39), [#122](https://github.com/mdastpak/Crypto-Exchange/issues/122)).
- **Breaking:** a key that appears twice in the same mapping of a configuration file now stops the server, with a message that names both lines. Before, one of the values silently won. The configuration files in the repository have no duplicated keys ([#122](https://github.com/mdastpak/Crypto-Exchange/issues/122)).
- The configuration package moved from `config` to `internal/config`, like every other package of the module. `config/` now holds only YAML files and the embed of `config.example.yaml`: `configs/assets.yaml` and `configs/aml_rules.yaml` moved there, and `assets.registry_path` and `compliance.aml.rules_path` default to `config/assets.yaml` and `config/aml_rules.yaml`. A local configuration that sets the old paths must be updated; nothing reads these files yet ([#123](https://github.com/mdastpak/Crypto-Exchange/issues/123)).
- **Breaking:** the server checks its whole configuration before it connects to anything, and stops with one list of every problem, one per line, each naming the setting and its environment variable. Besides missing settings, it now refuses values out of range (ports, timeouts, pool sizes, rate limits, an access token lifetime over a day, a refresh token shorter than the access token) and a TLS certificate and key that do not load. In release mode it also refuses: no TLS (`server.tls.enabled`, or the new `server.tls.behind_proxy` with `server.trusted_proxies` when a reverse proxy terminates TLS); `postgres.sslmode` other than `require`, `verify-ca`, or `verify-full`; an empty or default PostgreSQL password; an empty Redis password; the RabbitMQ `guest` account; `"*"` or non-`https` origins in `server.cors.allowed_origins` and `websocket.allowed_origins`; and private key files that other users may write to. The OTP and key provider checks of release mode are reported in the same list. A release deployment that relied on any of these must change its configuration; `docs/configuration.md` lists the rules under *Release mode* ([#41](https://github.com/mdastpak/Crypto-Exchange/issues/41)).
- The WebSocket gateway follows its configuration and bounds what each client can do ([#47](https://github.com/mdastpak/Crypto-Exchange/issues/47)). The inbound message size (`websocket.max_message_size_bytes`, now 4 KiB by default instead of an unused 1 MiB), the ping interval, and the new `write_timeout_seconds` replace the hard-coded values of 512 bytes, 30 seconds, and 10 seconds. Each connection may send `client_messages_per_second` (10) with bursts of `client_message_burst` (20), and a faster client is disconnected with close code `1008`. Each instance accepts at most `max_connections` (10000) connections, and `max_connections_per_ip` (20) per client address; further upgrades get `503` and `429`. A connection may bring a user access token, as `Authorization: Bearer` or, from a browser, as the subprotocols `access_token` and the token, never in the URL. The token gets the checks of the `/user/*` routes, and a refused token gets `401` or `403` before the upgrade. A client's time zone is validated and loaded once instead of on every ping, and `Shutdown` may be called more than once.
- **Breaking (domain model):** the balance model is a state machine ([#43](https://github.com/mdastpak/Crypto-Exchange/issues/43)). Before, withdrawals subtracted from `OnChain` and never released locked funds, deposits never became available, and `Total` counted locked and on-chain funds twice. `Balance.Apply` now performs one of nine transitions: deposit detected, credited, or failed; lock and unlock; trade credit, trade debit, and fee; and withdrawal completed. Each moves a positive amount, refuses to make any component negative without changing anything, and returns a change event with the components and versions before and after. The total is available plus locked. `OnChain`, which mixed the custody location of funds with what the user owns, is removed. Migration 17 has the database enforce the same rules: amounts are never negative, `total` is a generated column, on-chain columns are dropped, and a user has one balance per asset also without a sub-account. Before, NULL sub-accounts allowed duplicates. Nothing writes balances yet; the ledger is [#60](https://github.com/mdastpak/Crypto-Exchange/issues/60).

### Fixed

- First-time OTP sign-in failed with `500 Failed to create user`, because the `users.info` constraint from migration 2 required `username` and `password` keys that OTP sign-in never writes. Migration 11 requires a contact object in `users.info`, makes each contact value unique (email addresses and usernames case-insensitively), and stops with an actionable message if manually inserted rows conflict with these rules. Concurrent first sign-ins for the same contact now resolve to one user ([#8](https://github.com/mdastpak/Crypto-Exchange/issues/8)).
- RabbitMQ publishing stalled after about three messages, and graceful shutdown could hang, because every `Publish` call registered a new publisher-confirm listener that was never removed, and the library delivers each confirmation to every listener with a blocking send. Each channel now has a single listener whose confirmations are routed to the waiting publish by delivery tag, so concurrent publishes are pipelined and each one waits only for its own confirmation. A channel closed by the broker is replaced on the next publish ([#9](https://github.com/mdastpak/Crypto-Exchange/issues/9)).
- Signing in to a disabled, deleted, or suspended account returned `500 Failed to create user`. It now returns `403` with a stable message ([#15](https://github.com/mdastpak/Crypto-Exchange/issues/15)).
- The Docker image could not be built, because the Dockerfile used Go 1.22 while `go.mod` requires Go 1.26, and the `app` service of `docker-compose.yml` could not reach its dependencies or read its keys. The image now builds both `server` and `admin` and includes the migrations. The `app` service uses `config/config.compose.yaml`, receives the user keys as Compose secrets, and starts with every dependency healthy. The Redis health check uses `PING` instead of `INCR`, RabbitMQ receives its Erlang cookie on the command line, which avoids the `.erlang.cookie` `eacces` failure on some Docker Desktop and WSL 2 setups, and the obsolete `version` key is gone ([#28](https://github.com/mdastpak/Crypto-Exchange/issues/28)).
- WebSocket clients never received currency events, because the server never started the RabbitMQ consumer. The consumer now starts with the server and stops before RabbitMQ closes. It uses a channel of its own with a prefetch limit, and an exclusive, auto-delete queue per server instance instead of the shared durable `ws_price_updates` queue, so clients on every instance receive every event. It subscribes before startup completes and subscribes again with backoff when its channel closes ([#19](https://github.com/mdastpak/Crypto-Exchange/issues/19)).
- When several messages were queued for a WebSocket client, they were written into one frame back to back, which is not valid JSON. Each message is now a frame of its own ([#20](https://github.com/mdastpak/Crypto-Exchange/issues/20)).
- `RabbitMQService` raced on its connection and channel during reconnects: they were guarded by two different mutexes, the close notification was replaced while being read, the replaced connection was never closed, and a channel closed by the broker was reported as healthy and never replaced. One supervisor goroutine now owns reconnection, watches both the connection and the publishing channel, closes replaced connections, and restores the channel after a channel-level error without waiting for a publish. The health check reports RabbitMQ as degraded while either is unavailable, and publishes wait up to five seconds for the channel instead of failing at once ([#21](https://github.com/mdastpak/Crypto-Exchange/issues/21)).
- Creating or updating a currency with a duplicate symbol or contract, or with invalid data, returned `500`: the handlers matched `lib/pq` errors, while the driver is pgx, and they did not validate requests, so a missing `status` failed in the database. Database errors are now matched by SQLSTATE code: a duplicate returns `409` with a stable code (`duplicate_symbol` or `duplicate_contract`) and the field. Requests are validated with field-level errors, `status` defaults to `pending`, symbols are stored in upper case, and server-controlled or unknown fields are rejected ([#22](https://github.com/mdastpak/Crypto-Exchange/issues/22), [#23](https://github.com/mdastpak/Crypto-Exchange/issues/23)).
- Currency updates could not set `is_token` or `if_fiat` back to `false`; only the fields sent are changed now, which a test checks for every field alone ([#35](https://github.com/mdastpak/Crypto-Exchange/issues/35)). The stored row is locked while an update is applied, so concurrent partial updates of one currency no longer overwrite each other.
- Currencies that were not approved were public: create and update cached every currency, whatever its status, and public and user routes returned everything in the cache, so a `pending` or `suspend` currency was visible until the next restart, and every change was announced to WebSocket clients. Only approved currencies are cached now, and a currency that is suspended, set back to pending, or deleted leaves the cache at once. Public and user routes also skip any cached currency that is not approved. WebSocket events follow what public clients can see: a currency that becomes approved is announced as `create`, one that stops being approved as `delete`, and changes to currencies that are not approved are not announced. A delete locks the row, so concurrent deletes of one currency succeed only once ([#24](https://github.com/mdastpak/Crypto-Exchange/issues/24)).
- Stopping any server instance deleted the currency cache, which all instances share and which is the only source of public currency reads, so during a rolling deploy the other instances listed no currencies until one of them restarted. Shutdown now leaves the cache alone. At startup, an instance still refreshes the cache from the database and removes the entries of currencies that are not approved, but without clearing it, and it keeps any entry that another instance wrote meanwhile ([#25](https://github.com/mdastpak/Crypto-Exchange/issues/25)).
- Every `/public` route counted against the sign-in limit of five requests per minute and client IP, so a client could read the currency list only five times per minute, and reading it used up the budget for signing in. Currency reads, token refresh, and logout are now only subject to the general REST limit. Sign-in code requests (`POST /public/auth`, `POST /admin/auth`) are limited by `rate_limits.auth.otp_requests_per_hour` in a one-hour window, which was parsed but never applied, and code verifications by `rate_limits.auth.login_attempts_per_minute`. Each route counts separately, so user sign-in cannot use up the budget of admin sign-in. These windows are now fixed: every request used to restart the expiry, so a blocked client that kept retrying stayed blocked, which a one-hour window would have made far worse ([#26](https://github.com/mdastpak/Crypto-Exchange/issues/26), item 2 of [#34](https://github.com/mdastpak/Crypto-Exchange/issues/34)).
- Rolling back migration 8 alone deleted `users.status` and the status of every user. Migration 2 created that column, so migration 8 never added it, but its down migration dropped it anyway; applying 8 again then created it with another type and default, which broke sign-in. The down migration now drops the column only if migration 8 created it, and drops the index migration 8 created on it. The down migration of migration 3 now also drops the `update_updated_at_column()` function that migration 3 creates. A new test rolls back and re-applies every migration one step at a time and compares the schema after each step ([#30](https://github.com/mdastpak/Crypto-Exchange/issues/30)).
- `/` and `/swagger/*` had no security headers, no CORS policy, and no rate limit, because they were registered before the global middleware, which Gin applies only to later routes. All global middleware is now registered before any route, and a test sends a request to every route and checks its headers ([#32](https://github.com/mdastpak/Crypto-Exchange/issues/32)).
- `/system/healthcheck` answered `200` also when PostgreSQL, Redis, or RabbitMQ was down, so load balancers, orchestrators, and the Docker `HEALTHCHECK` treated a broken instance as healthy. The new `/system/ready` answers `503` while a dependency is unavailable, and `/system/healthcheck` now answers the same way. The new `/system/live` checks no dependency, for liveness probes. The checks run at once, each within two seconds, and the details per dependency are left out in release mode. The image's `HEALTHCHECK` uses `/system/ready` instead of `/system/ping` ([#33](https://github.com/mdastpak/Crypto-Exchange/issues/33)).
- The rate limiter had several defects. The limit on `/user/*` and `/admin/*` was keyed by IP address, because it read a `user_id` that no middleware set; it now uses the subject and role of the access token, so users behind one address no longer share a budget. Rates above 1000 per second divided by zero, because the token bucket refilled in whole milliseconds per token; it now counts fractions of a token. The Lua script was rebuilt on every request; it is loaded once. `Retry-After` was truncated to `0` for waits under a second; it is rounded up. `X-RateLimit-Remaining` is now set on token-bucket responses too. Every Redis error let the request through; the new `rate_limits.<limiter>.on_error` setting chooses between `allow` and `deny` (`503`), with `deny` for the sign-in limits and `allow` for the others by default ([#34](https://github.com/mdastpak/Crypto-Exchange/issues/34)).
- Only one currency could have an empty contract, because the unique index on `contract` covered empty strings. Migration 13 makes only non-empty contracts unique, so native coins and fiat currencies can coexist ([#22](https://github.com/mdastpak/Crypto-Exchange/issues/22)).
- While Redis was unreachable, every request waited for the Redis client's default timeouts and retries: `/system/live` answered after five seconds, `/system/ready` did not answer before the server closed the connection, and the other routes were delayed by seconds. Each rate limiter now gives up on Redis after `rate_limits.timeout_ms` (250 ms by default), and its `on_error` setting decides. The limiters of one request, such as the REST and sign-in limits, wait at most once together. The health probes under `/system` are counted in the memory of each instance instead of in Redis, so they answer at once, and `/system/ready` reports the outage with `503` within its two-second check. The client's timeouts and retries are configurable with the new `redis.dial_timeout_ms`, `read_timeout_ms`, `write_timeout_ms`, `pool_timeout_ms`, and `max_retries` settings, which default to one second for dialing, reading, and writing, two seconds for a free connection, and one retry, instead of the library's five seconds, three seconds, and three retries ([#119](https://github.com/mdastpak/Crypto-Exchange/issues/119)).
- 19 Go files were not formatted with `gofmt`. Go sources and `go.mod` and `go.sum` now keep LF line endings on every platform, so that `gofmt -l` and `go mod tidy -diff` give the same result on Windows as in CI ([#36](https://github.com/mdastpak/Crypto-Exchange/issues/36), part of [#40](https://github.com/mdastpak/Crypto-Exchange/issues/40)).
- If releasing the migration lock failed, the error was ignored, and the connection, which might still hold the session-scoped lock, went back to the pool, where it would block every later migration. The failure is now logged, and the connection is discarded. The WebSocket pumps now end a connection whose read or write deadline cannot be set, instead of ignoring the error ([#40](https://github.com/mdastpak/Crypto-Exchange/issues/40)).
- `admin disable` said that the administrator's tokens stay valid until they expire. They are rejected from their next request on, since the admin routes check the administrator on every request ([#18](https://github.com/mdastpak/Crypto-Exchange/issues/18)); the message now says so.
- `KYCProfile.CanUpgrade` compared tiers as strings, where `BASIC < ENHANCED < INSTITUTIONAL < NONE < STANDARD`. A new user at `NONE` could never upgrade, `STANDARD` could not move to `ENHANCED`, and `BASIC` could "upgrade" to `NONE`. Tiers now have a rank (`KYCTier.Rank`), unknown tiers are refused, and a user at `NONE` may apply unless an application is under review, while a higher tier must be approved first ([#42](https://github.com/mdastpak/Crypto-Exchange/issues/42)).
- Domain helpers misbehaved on edge values ([#44](https://github.com/mdastpak/Crypto-Exchange/issues/44)). A maximum order size or withdrawal of `0`, the column default, rejected everything instead of meaning no maximum. Zero-decimal assets such as IRR were never rounded. An order with a quantity of `0` or less passed when the market had no minimum. A negative price, tick size, or lot size was not caught, and market orders skipped the minimum notional even when the expected price was known. `Decimal.Div` and `QuoRem` panicked on a zero divisor and now return `ErrDivisionByZero`, and `Decimal.Pow` returned `0` for undefined powers such as `0^0` and now returns an error. `Decimal` accepts JSON numbers as well as strings, parsed from their text without float rounding. The Go settlement modes `LAYER2` and `BATCH`, which the database enum does not have, are removed, and a test now compares every database enum with its Go constants. The custody provider interface takes a `context.Context` instead of its own `Context` type, which shadowed it and could not be cancelled. Ethereum finality is 64 blocks (two epochs), not 2.
- The asset registry, `config/assets.yaml`, defined `USDT` twice and listed a USDC contract that is not Circle's (`0xA0b86a33...`), which would have sent funds to an arbitrary address once the file is used for custody. The registry now defines each asset once, with one entry per network (USDT on TRON and on Ethereum), and the contract addresses match what Tether, Circle, and Etherscan publish. The new `internal/assetregistry` loads the file and refuses it on any problem, reporting every problem at once. It checks unique symbols, networks, contracts, and markets; known types, statuses, and networks; Ethereum addresses by their EIP-55 checksum and TRON addresses by their Base58Check checksum; consistent limits and fees; and markets of known assets ([#46](https://github.com/mdastpak/Crypto-Exchange/issues/46)).
- Shutdown could drop requests and skip closing the services ([#49](https://github.com/mdastpak/Crypto-Exchange/issues/49)). Load balancers kept routing to a stopping instance until it refused connections. WebSocket clients were disconnected without a close frame, before the HTTP server stopped. A server that failed to listen, and every failure at startup after the services were connected, exited at once without closing anything. Now `/system/ready` answers `503` with `"status": "draining"` first, and the instance keeps serving for the new `server.drain_seconds` (`SERVER_DRAIN_SECONDS`, 0 by default) before it stops accepting connections. Then the requests in flight complete, the delivery worker stops, and WebSocket clients get a close frame with code `1001` (going away) before RabbitMQ, Redis, and PostgreSQL close, in that order. So does a client whose upgrade was in progress when the shutdown started, which could before be registered after the shutdown and never be closed. The whole shutdown takes at most the new `server.shutdown_timeout_seconds` (`SERVER_SHUTDOWN_TIMEOUT_SECONDS`, 30 by default, as before), and each step runs even when an earlier one fails. A server that fails goes through the same steps, without the drain, and a failure at startup closes what was opened before it. Stopping one instance leaves the others serving: it closes only its own connections and deletes nothing shared in Redis or RabbitMQ, and the sign-in codes it has not delivered go back to the shared queue for the other instances. Release mode warns at startup when `server.drain_seconds` is 0. The `app` service of `docker-compose.yml` waits 40 seconds before Docker kills it, instead of 10, so that the shutdown can finish. The Redis service may be closed more than once, like the others.
- The public currency routes read only the Redis cache. A Redis flush, the 24-hour expiry of an entry, or a failed cache write made currencies disappear until the next restart, and listing scanned the whole Redis keyspace with one more round trip per currency ([#52](https://github.com/mdastpak/Crypto-Exchange/issues/52)).
  - The new `internal/currencies` reads the list from one Redis key that every instance shares, in one round trip, and loads it from PostgreSQL whenever it is not cached. While Redis is unavailable, the routes read PostgreSQL instead; each Redis call of a read gives up after 250 ms.
  - Instances do not load and write the list at the same time. Only the instance that holds a lock in Redis loads a missing list; the others wait for it, or read PostgreSQL without writing after two seconds, for example when the loading instance stopped. Concurrent misses within an instance share one wait or load.
  - An admin change to a currency that was or becomes public drops the list after its commit. A generation counter keeps a load that began before a change from caching the old list.
  - The list is fresh for the new `redis.currency_cache_ttl_seconds` (`REDIS_CURRENCY_CACHE_TTL_SECONDS`, 300 by default). After that, one request, on one instance, refreshes it while every other request is served the old list, so that no burst of misses follows its end. This bounds how long a failed drop, or a change made directly in the database, leaves it out of date. Startup no longer syncs the cache.
  - In the benchmark, listing 100 cached currencies takes about 0.6 ms instead of 38 ms.
  - The list is ordered oldest first. `id`, `created_at`, and `updated_at` are now filled from the database; they were 0 and empty for currencies cached by an admin change.
  - `GET /public/currencies/{hk}` answers `400` for an hk that is not a UUID, instead of `404`. Both routes answer `503` instead of `500` when neither the cache nor PostgreSQL can be read.
  - The old `base_definitions:currency:*` keys are not deleted, so that instances of the previous version keep serving during a rolling deploy. They expire within a day.
  - The Redis client dials once per attempt (`DialerRetries: 1`), as go-redis v8 did. go-redis v9 dials up to five times by default, so a command could wait five times `redis.dial_timeout_ms` while Redis was unreachable.
- A currency change whose event could not be published, because RabbitMQ was unavailable, was committed without its event, and nothing published it later; a failed drop of the cached list was not retried either ([#89](https://github.com/mdastpak/Crypto-Exchange/issues/89), first part).
  - The admin currency routes now write the event to the new transactional outbox, `outbox_events` (migration 18), in the transaction of the change. So the event exists if and only if the change commits.
  - The new `internal/outbox` relay publishes the messages in id order, holding back the later messages of a topic while one fails. It retries with a backoff from 1 s up to 5 minutes, and drops the cached currency list before it publishes, which retries a failed drop too. Published messages are deleted after seven days.
  - Every instance runs a relay, and one at a time relays, under a transaction-scoped advisory lock. A message is never published by two instances, and an instance that stops leaves its messages to the others. The relay stops after the HTTP server at shutdown.
  - Delivery is at least once. Currency events carry a new `id`, a version 7 UUID, that the WebSocket gateway forwards, so that clients can drop a repeated event.
  - Creating a currency now runs in a transaction, like updates and deletes.

### Security

- A user whose account was soft-deleted (`deleted_at` set) could still sign in with a code, because user sign-in only checked the status. Sign-in now refuses deleted accounts, as the profile routes and admin sign-in already did ([#38](https://github.com/mdastpak/Crypto-Exchange/issues/38)).
- Gin 1.12.0 brings in `github.com/quic-go/quic-go`, whose v0.59.0, the version gin asks for, has a memory exhaustion in HTTP/3 QPACK trailer handling (GO-2026-5676). The module is pinned to v0.59.1, which fixes it. The vulnerability scan found it in the Dependabot update.
- `golang.org/x/net` is updated from v0.58.0 to v0.60.0, which fixes four vulnerabilities of the HTTP/2 server that the server's code reaches: a crash from a race in the HPACK encoder (GO-2026-6617), a double flow-control refund (GO-2026-6612), CPU exhaustion from repeated window changes (GO-2026-6611), and memory exhaustion from trailer headers (GO-2026-6603). The first run of the new vulnerability scan found them ([#36](https://github.com/mdastpak/Crypto-Exchange/issues/36)).
- The Swagger UI was served in release mode too. It is now served only outside release mode, unless `server.swagger.enabled` (`SERVER_SWAGGER_ENABLED`) says otherwise. A client-supplied `X-Request-ID` was accepted as it was, so a value with line breaks or quotes could forge entries in the log. Only IDs of up to 64 letters, digits, and `.`, `_`, `:`, or `-` are kept; any other ID is replaced by a UUIDv7, which also replaces the nanosecond timestamp the server generated before. Request bodies are limited to `server.max_body_bytes` (`SERVER_MAX_BODY_BYTES`, 1 MiB by default), and a larger body gets `413` ([#32](https://github.com/mdastpak/Crypto-Exchange/issues/32)).
- `db.NewTestPostgresService`, which dropped and recreated `users` in whatever database it was given, was compiled into the server binary. It is removed. Tests build their schemas with the real migrations, through the new test-only `internal/testutil/pgtest` package, which refuses to empty a database whose name does not start with `testdb_`. A test checks that the code of the server and of the admin command contains no `DROP TABLE`, `DROP SCHEMA`, `DROP TYPE`, `DROP DATABASE`, or `TRUNCATE` statement and does not depend on a test helper ([#31](https://github.com/mdastpak/Crypto-Exchange/issues/31)).
- Refresh tokens were accepted as access tokens, giving seven days of API access, and were never revoked, not even by logout. Tokens now carry a type (`typ`), so protected routes accept only access tokens and the refresh endpoint accepts only refresh tokens. Each sign-in creates a session in the `sessions` table. Refresh tokens are rotated on every use, and presenting an already rotated refresh token revokes the session. Logout revokes the session and clears the cookie ([#10](https://github.com/mdastpak/Crypto-Exchange/issues/10)).
- Every IP-based rate limit, including the OTP sign-in limit, could be bypassed by sending a different `X-Forwarded-For` value on each request, because the limiter read that header directly and Gin trusted forwarding headers from every peer. The limiter now uses the client address that Gin derives from the connection, and forwarding headers are trusted only from the proxies listed in the new `server.trusted_proxies` setting (none by default) ([#11](https://github.com/mdastpak/Crypto-Exchange/issues/11)).
- With no allowed origins configured (the default), the CORS middleware reflected every `Origin` together with `Access-Control-Allow-Credentials: true`, so any website could make credentialed requests and read the responses. A `"*"` entry had the same effect. The middleware now fails closed: only listed origins are allowed, `"*"` and malformed origins stop the server at startup, and responses carry `Vary: Origin` ([#12](https://github.com/mdastpak/Crypto-Exchange/issues/12)).
- Every OTP request wrote the sign-in code together with the raw email address, phone number or username to the application log, so anyone with log access could sign in as any user. Codes are now handed to an `OTPSender`, which discards them by default. The new `otp.auth.dev_log_codes` setting writes them to the log with a masked contact for local development only, and the server refuses to start with it in release mode ([#13](https://github.com/mdastpak/Crypto-Exchange/issues/13)).
- Anyone could create or take over a username-only account, because a username cannot receive a code, so the code proved nothing about who was signing in. Username sign-in is removed ([#14](https://github.com/mdastpak/Crypto-Exchange/issues/14)).
- OTP verification allowed more guesses than `otp.auth.retry_limit`: the attempt counter was read and written back without atomicity, so parallel requests all saw the same count, and every new code came with a fresh session and a fresh budget. Each attempt is now reserved atomically before the code is checked, both for the code and for its contact, and the new `otp.auth.contact_requests_per_hour` and `otp.auth.contact_attempts_per_hour` settings bound codes and attempts per contact across sessions. A code also signs in only once when it is sent in parallel. Redis keys contained the code itself; sessions now store an HMAC of the code and the contact encrypted with AES-GCM, both keyed by the new `otp.auth.secret`. Code digits were slightly biased towards 0 to 5; they are now uniform ([#15](https://github.com/mdastpak/Crypto-Exchange/issues/15)).
- The contact stored during OTP sign-in was encrypted with a key derived from the session UUID, which the client receives, so the encryption protected nothing, and its 100,000 PBKDF2 iterations ran twice per sign-in on unauthenticated endpoints, which made them a cheap way to exhaust the CPU. The contact is now encrypted with a key derived from `otp.auth.secret`, without a per-request KDF, and a test keeps password-hashing KDFs out of the code behind unauthenticated requests. A panic returned its value and stack trace outside release mode when `RecoveryMiddleware` was used; it now returns only `500 Internal server error`, in every mode, and the router uses it [#16](https://github.com/mdastpak/Crypto-Exchange/issues/16).
- Token verification accepted any RSA algorithm and did not check the issuer, the audience, or the presence of an expiry, and admin and user tokens were signed with the same key, so anyone holding the user key could mint admin tokens. Tokens are now verified by a single `ParseToken` that requires RS256, the configured issuer, the audience of the route's role, an expiry, the expected token type and role, and a `kid` that names a key of that role. The key state was written outside its mutex; it is now replaced atomically ([#17](https://github.com/mdastpak/Crypto-Exchange/issues/17)).
- The repository had no `.dockerignore`, so `.env` files, private keys, and local configuration were copied into the image build, and the final image copied the whole `config/` directory, including any local configuration with secrets. A `.dockerignore` now keeps them out of the build context, and the image holds no configuration. It runs as an unprivileged user (UID 10001) and installs no packages: the time zone database is embedded in the binaries ([#28](https://github.com/mdastpak/Crypto-Exchange/issues/28)).
- Access tokens stayed valid until they expired after their session ended or their user was disabled. Logout blacklisted only the token it was called with, so the access token from before the last refresh kept working; a session revoked for refresh token reuse left the attacker's access tokens working; and a disabled, suspended, banned, or deleted user kept access to `/user/*`. The user routes, except `/user/logout`, now check the session and the user in the database on every request (`RequireActiveSession`), as the admin routes check the administrator: a token of an ended session gets `401 Unauthorized - Session is not active`, and a token of a user who can no longer sign in gets `403`. This also applies to changes made directly in the database. Refresh answers `403` for such a user and issues no new tokens. A deleted user now gets `403` from the profile routes instead of `404`. Logout still works for a disabled user, so the session can be ended ([#120](https://github.com/mdastpak/Crypto-Exchange/issues/120)).
- The WebSocket gateway forwarded any JSON object from the `price_updates` exchange to every client, so anything that could publish there, such as a misconfigured service or a leaked broker credential, could push arbitrary fields and content to all clients. It now rebuilds each event from the currency event schema (`entity`, `action`, `hk`, `info`, and its own `server_time`), drops unknown fields, and drops and logs events with an unknown entity or action, an `hk` that is not a canonical UUID, an `info` that does not fit the action, or more than 16 KiB. The schema is shared with the admin handler that publishes the events, as `models.CurrencyEvent` ([#121](https://github.com/mdastpak/Crypto-Exchange/issues/121)).
- The API key model leaked and kept secrets: a key ID was built from the first four bytes of its secret, `HashAPIKeySecret` returned the secret unchanged, so `api_keys.secret_hash` would have held it in plaintext, `VerifyAPIKeySecret` compared in variable time, and Ed25519 keys were random bytes instead of key pairs. Key IDs are now 128 random bits, independent of the secret. Ed25519 keys are real key pairs, and only the public key is kept, or a key the client uploads. An HMAC secret, which the server needs to verify signatures, is sealed with a `field-enc` data key and bound to its key ID. Signatures are checked in constant time. Migration 16 replaces `secret_hash` with `secret_sealed` and `ed25519_public_key`, and refuses to run while API key rows exist; the API does not issue API keys yet ([#45](https://github.com/mdastpak/Crypto-Exchange/issues/45)).
