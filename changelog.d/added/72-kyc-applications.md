- KYC applications for level 2 ([#72](https://github.com/mdastpak/Crypto-Exchange/issues/72)). See [KYC applications](docs/api.md#kyc-applications).
  - A user at level 1 opens an application with their address, occupation, and source of funds (`POST /user/kyc/applications`), adds documents (`POST /user/kyc/applications/{id}/documents`: a JPEG, a PNG, or a PDF of at most 10 MB, by its content), and submits it once it has an identity document, a selfie, and a proof of address. `GET /user/kyc` shows it.
  - Administrators list the applications that wait (`GET /admin/kyc/applications`), read one with its form (`GET /admin/kyc/applications/{id}`, audited), open its documents through a link signed for them for a minute (`GET /admin/kyc/documents/{id}/link`), and approve it, which raises the user to level 2 in the same transaction, or reject it with a reason that the user reads. Both need a step-up.
  - Personal data is never stored or logged in plaintext: the form is sealed with the field key, and each document is encrypted by the server before it is stored in the S3-compatible storage of `compliance.kyc.storage`, which encrypts it again with SSE-S3. The name of a file is not kept. The row of a document seals the SHA-256 of what was stored, so an object swapped in the storage is refused.
  - Migration 52: the `*_enc` columns of the KYC tables become `BYTEA`; the applications and documents are sealed from their first row; `integrity_findings` accepts the two tables.
  - `KYC_STORAGE_ACCESS_KEY` and `KYC_STORAGE_SECRET_KEY` set the keys of the storage; release mode reaches it over HTTPS.
  - The contract check of the end-to-end tests accepts a file response of a documented `{file}` schema.
